Real-Time Mempool Monitoring for
Zero-Confirmation Risk Interception

How FidesOrigin watches the mempool to stop risky transactions before a single block confirmation — and why traditional post-confirmation analysis is too late.

FidesOrigin Engineering · August 2026 · 10 min read

What Is the Mempool?

Before a transaction is included in a block and committed to the blockchain, it sits in a temporary holding area called the mempool (memory pool). Every full node maintains its own mempool, a dynamic buffer of pending transactions waiting to be mined.

When a user broadcasts a transaction, it propagates across the peer-to-peer network and lands in the mempools of thousands of nodes. Miners select transactions from their local mempool to include in the next block, typically prioritizing those with the highest gas fees. Until that block is mined, the transaction is "unconfirmed" — it exists in the network's consciousness but not in its permanent record.

This unconfirmed state is both a feature and a vulnerability. It's a feature because it enables rapid propagation and fee-market dynamics. It's a vulnerability because a transaction in the mempool can still be executed — and if it's destined for a sanctioned address, a phishing contract, or a known exploit, waiting for block confirmation means the damage is already done.

The Zero-Confirmation Problem

Traditional crypto compliance follows a simple workflow:

  1. Transaction is broadcast to the network
  2. Transaction is included in a block (12 seconds on Ethereum, ~10 minutes on Bitcoin)
  3. Transaction receives 1–3 confirmations
  4. Risk platform queries the transaction hash against its database
  5. Compliance team reviews the alert
  6. Action is taken (if any)

By step 6, the funds have already moved. The compliance team is documenting a crime, not preventing one. For high-speed chains like Base or Polygon, the entire sequence from broadcast to finality can take under 3 seconds. Human-in-the-loop compliance cannot keep up.

This is the zero-confirmation gap: the window between transaction broadcast and block inclusion where traditional tools are blind and manual intervention is impossible. FidesOrigin closes this gap by moving the decision point from after confirmation to before inclusion.

Key Insight

On Ethereum, a standard ERC-20 transfer is confirmed in ~12 seconds. But the transaction is visible in the mempool within 200–500ms of broadcast. That 200ms window is all FidesOrigin needs to evaluate and intercept.

1. Full-Node WebSocket Connection

The Watcher maintains persistent WebSocket connections to geographically distributed full nodes on each supported network. We use eth_subscribe with the newPendingTransactions topic to receive a stream of transaction hashes as they enter the mempool.

WebSocket Subscription (TypeScript)
// Connect to Ethereum full node via WebSocket const ws = new WebSocket("wss://eth-mainnet.g.alchemy.com/v2/..."); ws.on("open", () => { ws.send(JSON.stringify({ jsonrpc: "2.0", id: 1, method: "eth_subscribe", params: ["newPendingTransactions"] })); }); ws.on("message", async (data) => { const { params: { result: txHash } } = JSON.parse(data); // txHash is a pending transaction — evaluate immediately await evaluateTransaction(txHash); });

2. Transaction Parsing & Decoding

Each pending transaction hash is immediately fetched via eth_getTransactionByHash to retrieve the full transaction object: sender, recipient, value, data payload, and gas parameters. For ERC-20 transfers, the input data is decoded to extract the actual token recipient and transfer amount.

Transaction Decoding
// Decode ERC-20 transfer from input data const iface = new ethers.Interface(ERC20_ABI); const decoded = iface.parseTransaction({ data: tx.input }); if (decoded?.name === "transfer") { const [to, amount] = decoded.args; // 'to' is the actual recipient, not necessarily tx.to await screenAddress(to, { sender: tx.from, amount: amount.toString(), token: tx.to, // token contract address network: "ethereum" }); }

3. Address Matching & Risk Scoring

Once the sender and recipient addresses are extracted, they are checked against the FidesOrigin Risk Registry in a two-phase process:

  • Phase 1 — Exact Match: Addresses are checked against the hotlist of sanctioned, phishing, and known-exploit addresses. This is an O(1) hashmap lookup taking <1ms.
  • Phase 2 — GNN Scoring: For addresses not on the hotlist, a Graph Neural Network evaluates the address's relationship graph (transaction neighbors, temporal patterns, counterparty risk). This produces a risk score from 0–100.
Risk Evaluation Pipeline
async function evaluateTransaction(txHash: string): Promise<RiskResult> { const tx = await provider.getTransaction(txHash); const { from, decodedTo, value } = parseTransaction(tx); // Phase 1: Exact match against hotlist const hotlistHit = await riskRegistry.isSanctioned(decodedTo); if (hotlistHit) { return { action: "BLOCK", reason: "SANCTIONED_ADDRESS", latencyMs: 12 }; } // Phase 2: GNN relationship scoring const score = await gnnModel.scoreAddress(decodedTo, { depth: 2, // 2-hop neighborhood timeWindow: "24h", minTxCount: 3 }); if (score.value > 85) { return { action: "QUARANTINE", reason: "HIGH_RISK_GNN", score, latencyMs: 67 }; } return { action: "PASS", score, latencyMs: 67 }; }

4. Alerting & On-Chain Interception

For transactions that pass the risk threshold, two response paths exist:

  • Alert Mode: The transaction is flagged and an alert is sent via Webhook, PagerDuty, or Slack. The transaction proceeds but is logged for review.
  • Interceptor Mode: For integrated protocols (e.g., CompliantStablecoin), the Guard module is triggered. If the protocol supports pre-flight checks, the transaction is blocked at the smart contract level before it can execute.

Relationship to Flashbots

A common question: how does mempool monitoring relate to Flashbots and MEV (Maximal Extractable Value)?

Flashbots vs FidesOrigin MempoolWatcher

Flashbots watches the mempool to extract value — identifying arbitrage opportunities, sandwich attacks, and liquidation profits. Its goal is economic: capture MEV before others do.

FidesOrigin MempoolWatcher watches the mempool to prevent harm — identifying sanctioned addresses, phishing contracts, and suspicious patterns. Its goal is protective: stop bad transactions before they confirm.

The two are not competitors. In fact, they are complementary:

  • Flashbots protects protocol economic integrity (no front-running, fair ordering)
  • FidesOrigin protects protocol regulatory integrity (no sanctioned addresses, compliant flows)

Flashbots' private mempool (Flashbots Protect) can even enhance FidesOrigin's effectiveness: if a protocol routes transactions through Flashbots Protect, FidesOrigin can still monitor the mempool for public transactions while the protocol's own transactions bypass public MEV extraction.

  • Transaction fetch: 25–40ms (RPC round-trip)
  • Input decoding: 1–3ms (local ABI parsing)

On faster chains like Base and Polygon, where block times are 2–3 seconds, the 100ms evaluation window represents only 3–5% of the total time to confirmation, leaving ample headroom for interception.

Limitations & Trade-offs

Mempool monitoring is powerful but not universal. We believe in transparent discussion of its boundaries:

  • Private mempools: Transactions sent via Flashbots Protect or private RPCs (e.g., Taichi Network) do not appear in the public mempool. These require protocol-level integration (Guard module) rather than mempool watching.
  • Network propagation variance: A transaction may reach some nodes before others. The Watcher must connect to multiple geographically distributed nodes to minimize miss rates.
  • Replace-by-Fee (RBF): A user can replace a pending transaction with a higher-fee version, potentially changing the recipient. The Watcher tracks transaction nonces to detect replacements.
  • Latency floor: RPC round-trips impose a physical floor on latency. Sub-50ms end-to-end requires co-located infrastructure, which is available in our Enterprise tier.

Conclusion

The mempool is the last frontier of pre-execution risk control. Every second a transaction spends in the mempool is a second during which it can be evaluated, scored, and — if necessary — stopped.

FidesOrigin's MempoolWatcher closes the zero-confirmation gap that traditional post-hoc analytics cannot address. Combined with the on-chain Guard module, it provides a two-layer defense: catch it in the mempool, and if that fails, stop it in the contract.

For stablecoin issuers, DeFi protocols, and any institution building on-chain, this is not a nice-to-have. It's the difference between compliance that documents breaches and compliance that prevents them.
