Guard 交易前检查
链上风控的新标准

FidesOrigin V2.1 推出交易前守卫（Pre-Transaction Guard）：在交易上链之前执行零损失风险拦截。不是事后，而是事前。

以下这个数字应该让每一位加密合规官感到恐惧：43亿美元。这是2024年在链上结算后被标记为非法交易的估计金额。当警报响起时，资金已经流失。钱包已空。线索已断。

事后交易分析——行业标准——从根本上说是一种取证练习。它告诉你出了什么问题。它不能阻止事情变糟。它是尸检，不是疫苗。

借助 FidesOrigin V2.1，我们正在改变这一等式。我们构建了一个在交易执行之前阻止不良交易的系统。不是在区块确认之后。不是在 DEX 兑换完成之后。而是在交易离开内存池之前。我们称之为交易前守卫（Pre-Transaction Guard）。

100倍乘数：预防 vs. 补救

让我们来谈谈为什么预防不仅更好——它在结构上是不同的。在事后交易筛查中，工作流程如下：

交易执行 → 区块被挖出 → 索引器捕获 → API 查询风险数据库 → 警报触发 → 合规团队调查 → 法律审查 → 追回尝试。

每个箭头都是一个延迟。每个延迟都是资金再次转移的机会。通过 Tornado Cash、跨链桥接到另一条链、通过十个混币地址进行剥离——当你的警报响起时，资金已经通过三个司法管辖区和一个隐私池被洗白。

传统 KYT 系统中，从交易执行到警报生成的平均时间？实时流程为47秒，批量筛查为4-6小时。在加密领域，47秒就是永恒。闪电贷攻击在单个区块内执行。MEV 三明治攻击在12秒内完成。你的合规警报只是赛后精彩回放。

交易前守卫颠覆了这一切。工作流程变为：

用户发起转账 → 守卫在交易执行之前评估风险 → 如果风险超过阈值 → 交易被拦截 → 零资金转移。

差异不是渐进的。它是根本性的。事后筛查衡量的是损失。交易前守卫防止损失发生。拦截一笔可疑交易的成本是一笔回滚的调用，仅需几千 gas。事后追回被盗资金的成本？通常不可能。有时数百万的法律费用。总是声誉损害。

数学很简单：一笔被阻止的200万美元非法转账，其节省的价值超过4万笔被拦截的50美元交易产生的合规费用。预防不仅更便宜——它是唯一真正有效的方法。

FidesCompliance V2.1 守卫架构

守卫系统不是附加组件。它是 FidesCompliance 中的一流架构层，采用与每个其他组件相同的可升级性、可审计性和故障安全原则设计。

其核心是 IPreTransactionGuard 接口——一个简洁的抽象，允许任何合规资产集成交易前风险评估，而无需触碰其核心转账逻辑。该接口定义了单一职责：给定一个交易意图，返回带有推荐操作（允许、警告或拦截）的风险评估。

IPreTransactionGuard.solSolidity 0.8.20
interface IPreTransactionGuard {
    enum Action { ALLOW, WARN, BLOCK }
    struct RiskAssessment {
        Action action; uint256 riskScore; uint256 confidence;
        string reason; uint256 assessmentTime; }
    struct TransactionIntent {
        address from; address to; uint256 value;
        address token; bytes data; uint256 chainId; }
    function assessTransaction(
        TransactionIntent calldata intent
    ) external view returns (RiskAssessment memory);
}

FidesCompliance 合约通过三个状态变量和一个专用代码路径集成守卫。以下是 previewTransaction() —— 纯预览功能 —— 的工作原理：

FidesCompliance.sol — previewTransaction()Solidity 0.8.20
function previewTransaction(
    address from, address to, uint256 amount,
    address token, uint256 deadline
) external view returns (bool allowed, uint256 riskScore) {
    // ... validation checks ...
    // V2.1: Guard pre-check — zero-gas fast path
    if (guardEnabled && address(guard) != address(0)) {
        IPreTransactionGuard.TransactionIntent memory intent =
            IPreTransactionGuard.TransactionIntent({
                from: from, to: to, value: 0,
                token: address(0), data: "", chainId: block.chainid });
        IPreTransactionGuard.RiskAssessment memory result =
            guard.assessTransaction(intent);
        if (result.action == IPreTransactionGuard.Action.BLOCK) {
            return (false, 100); // Direct intercept }
    }
    // 2. Risk Registry deep check (sanctions, risk scores)
    // ...
}

注意架构：守卫首先运行，在风险注册表检查之前。这是有意设计的。守卫专为速度优化——它维护一个紧凑的、频繁更新的高风险地址和模式缓存。如果守卫判定拦截，交易立即被阻止。无需进一步的存储读取。无需额外计算。快速路径就是快。

如果守卫通过（或被禁用），交易将落入现有的风险注册表和合规引擎评估。这种分层方法意味着你可以兼得两者：对明显威胁的亚50毫秒守卫拦截，以及对边缘案例的深度风险注册表分析。

守卫控制：启用、禁用、配置

守卫不是失控的流程。授权操作员可以通过简洁的管理界面完全控制它：

FidesCompliance.sol — Guard Admin FunctionsSolidity 0.8.20
/// @notice Set Guard contract address
function setGuard(address _guard) external onlyRole(ADMIN_ROLE) {
    guard = IPreTransactionGuard(_guard);
    emit GuardSet(_guard); }
/// @notice Enable/disable Guard pre-check
function setGuardEnabled(bool enabled) external onlyRole(ADMIN_ROLE) {
    guardEnabled = enabled;
    emit GuardEnabled(enabled); }
/// @notice One-click enable Guard
function enableGuard(address _guard) external onlyRole(ADMIN_ROLE) {
    guard = IPreTransactionGuard(_guard); guardEnabled = true;
    emit GuardSet(_guard);
    emit GuardEnabled(true); }
/// @notice One-click disable Guard
function disableGuard() external onlyRole(ADMIN_ROLE) {
    guardEnabled = false;
    emit GuardEnabled(false); }

这种设计赋予操作员精细的控制权。你可以部署新的守卫实现，并行测试，并通过单笔交易切换。你可以在维护或紧急情况下完全禁用守卫。你可以独立于主 FidesCompliance 合约升级守卫合约——两者都使用带有48小时时间锁的 UUPS 可升级性。

性能：低于50毫秒的承诺

让我们谈谈数字，因为在链上合规中，延迟不是锦上添花——它就是整个游戏。

守卫针对热路径执行进行了优化。它在合约内维护一个受制裁地址的 Merkle 树，由 Oracle 每5分钟更新一次。一次守卫检查是一次读取守卫地址的 SLOAD，一次对守卫合约的 staticcall，以及守卫内部的一些存储读取。总 gas：约8,000。总时间：在块时间低于一秒的任何 EVM 链上低于50毫秒。

作为对比：

  • Chainalysis KYT API：200-800毫秒往返（最佳情况）
  • Elliptic API：150-600毫秒往返
  • Chainlink Functions：1-3个区块延迟（以太坊上约12-36秒）
  • FidesOrigin 守卫：<50毫秒，零外部调用

守卫不仅更快——它属于完全不同的类别。它不调用任何东西。它读取链上状态。延迟受限于 EVM 的存储访问时间，而非网络往返或 API 速率限制。

对于 evaluateTransaction() 路径——实际执行检查的状态改变功能——守卫在与转账相同的交易上下文中运行。如果守卫拦截，整个交易回滚。无代币转移。无状态改变。调用者会看到一个来自守卫评估的清晰 TransactionBlockedError 及原因字符串。

实际影响：230万美元的拦截

理论是好的。以下是实际发生的情况。

一家使用 FidesOrigin 的大型稳定币发行商在2026年第二季度将守卫投入生产。在最初的30天内，守卫已处理120万次交易检查。其中，1,187笔被守卫标记为高风险。全部被阻止执行。

其中一笔被拦截的交易是一笔从新生成钱包到在 OFAC SDN 更新4分钟前被标记的地址的230万美元转账。Oracle 已将更新的 Merkle 根推送到守卫合约。守卫的 assessTransaction 调用识别出接收方为受制裁地址。转账通过一次回滚被阻止。从交易发起到阻止的总时间：23毫秒。

没有守卫，该交易将在链上结算。稳定币发行商将违反 OFAC 制裁。法律风险：重大。声誉损害：不可估量。追回成本：可能高达全部230万美元外加法律费用。

相反，发行商收到了自动警报："守卫阻止了向受制裁地址 0x... 的转账"。合规团队审查了它。拦截被确认为合法。事件在10分钟内结案。零资金转移。零监管风险。

这就是执行级合规的样子。不是报告。不是仪表板。而是一笔没有发生的交易。

守卫统计：默认透明

每次守卫检查和拦截都记录在链上，任何人都可以审计。合约维护运行计数器：

对于该稳定币发行商，30天的守卫统计数据如下：

  • 总检查次数：1,247,832
  • 被守卫拦截：1,187（0.095%）
  • 平均检查延迟：31毫秒
  • 误报率：0.003%（3笔交易经人工审查后解除拦截）
  • 预计防止损失：230万美元+（已确认）/ 870万美元+（预计额外可疑流）

这些数字不是抽象的。它们是一个将合规视为工程问题而非复选框的系统的输出。

为什么这改变了一切

守卫架构代表着我们对链上风险思考方式的转变。多年来，行业默认接受合规本质上是被动的。你执行一笔交易，然后检查它是否有问题。你能期望的最好结果就是快速检测。

交易前守卫拒绝了这一前提。它说：如果你能预测问题，你就能阻止它。区块链是确定性的。风险数据在链上。评估可以在相同的执行上下文中进行。没有技术理由将事后合规接受为标准。

对于稳定币发行商，这意味着晚上睡得更好。对于 DeFi 协议，这意味着在不牺牲用户体验的情况下提供机构级合规。对于监管机构，这意味着一个他们可以独立验证的透明、可审计、防篡改的合规层——无需 SOC-2 报告。

合规的 API 时代是关于信息的。守卫时代是关于执行的。信息告诉你发生了什么。执行阻止它发生。

我们不是在构建一个更快的警报系统。我们正在构建一个警报永远不需要触发——因为交易从未执行——的世界。
