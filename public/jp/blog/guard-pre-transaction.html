ガードによる事前取引チェック
オンチェーンリスク管理の新基準

FidesOrigin V2.1では、取引がチェーンに到達する前に実行されるゼロロスリスクインターセプト、Pre-Transaction Guardを導入しました。事後ではなく、事前です。

すべての暗号通貨コンプライアンス担当者を恐怖に陥れるべき数字があります：43億ドル。これは2024年にオンチェーンで決済された後にフラグが立てられた違法取引の推定価値です。アラートが発砲するまでには、資金は消えていました。ウォレットは空でした。痕跡は冷えていました。

業界標準である取引後分析は、根本的に鑑識の作業です。何が悪かったかを教えてくれます。しかし、悪いことを防ぐことはできません。これは解剖であり、ワクチンではありません。

FidesOrigin V2.1では、この方程式を変えます。悪い取引が実行される前に阻止するものを構築しました。ブロック確定後ではありません。DEXスワップ完了後ではありません。取引がメンプールを離れる前です。私たちはこれをPre-Transaction Guard（事前取引ガード）と呼びます。

100倍の乗数：予防対補救

なぜ予防が単に優れているだけでなく、構造的に異なるのかについてお話しします。取引後スクリーニングでは、ワークフローは次のようになります：

取引実行 → ブロック採掘 → インデクサーが取得 → APIがリスクデータベースをクエリ → アラート発砲 → コンプライアンスチームが調査 → 法的審査 → 回復の試み。

各矢印は遅延です。各遅延は資金が再び移動する機会です。Tornado Cash、別のチェーンへのブリッジ、10のミキサーアドレスを通じての剥離——アラートが発砲するまでには、資金は3つの管轄区域とプライバシープールを通じて洗浄されています。

従来のKYTシステムでの取引実行からアラート生成までの平均時間は？リアルタイムフローで47秒、バッチスクリーニングで4-6時間です。暗号通貨では、47秒は永遠です。フラッシュローン攻撃は単一ブロック内で実行されます。MEVサンドイッチは12秒で発生します。コンプライアンスアラートは試合後のハイライトリールです。

Pre-Transaction Guardはこれを逆転させます。ワークフローは次のようになります：

ユーザーが転送を開始 → ガードが実行前にリスクを評価 → リスクが閾値を超える場合 → 取引がブロックされる → 資金は移動しません。

違いは漸進的ではありません。カテゴリー的です。取引後スクリーニングは損害を測定します。Pre-Transaction Guardは損害の発生を阻止します。怪しい取引をブロックするコストは、数千ガスの還元呼び出しです。事後の盗まれた資金の回復コストは？多くの場合不可能です。時々数百万ドルの法律費用です。常に評判の損害です。

数学は単純です：1件の200万ドルの違法転送を阻止することで、4万件の50ドル取引が生成するコンプライアンス料金を上回る節約になります。予防は単に安いだけでなく——実際に機能する唯一のものです。

FidesCompliance V2.1 ガードアーキテクチャ

ガードシステムはアドオンではありません。FidesComplianceのファーストクラスアーキテクチャ層であり、他のすべてのコンポーネントと同じアップグレード可能性、監査可能性、フェイルクローズドの原則で設計されています。

その核心はIPreTransactionGuardインターフェースです——クリーンな抽象化により、任意のコンプライアントアセットがコア転送ロジックに触れることなく、事前取引リスク評価を統合できます。このインターフェースは単一の責務を定義します：取引意図が与えられた場合、推奨アクション（ALLOW、WARN、BLOCK）を伴うリスク評価を返します。

IPreTransactionGuard.sol Solidity 0.8.20 
interface IPreTransactionGuard {
    enum Action { ALLOW, WARN, BLOCK }

    struct RiskAssessment {
        Action action;
        uint256 riskScore;
        uint256 confidence;
        string reason;
        uint256 assessmentTime;
    }

    struct TransactionIntent {
        address from;
        address to;
        uint256 value;
        address token;
        bytes data;
        uint256 chainId;
    }

    function assessTransaction(
        TransactionIntent calldata intent
    ) external view returns (RiskAssessment memory);
}

FidesComplianceコントラクトは、3つの状態変数と専用のコードパスを介してガードを統合します。以下は、ビューのみのプレビュー関数previewTransaction()の動作方法です：

FidesCompliance.sol — previewTransaction() Solidity 0.8.20 
function previewTransaction(
    address from,
    address to,
    uint256 amount,
    address token,
    uint256 deadline
) external view returns (bool allowed, uint256 riskScore) {
    // ... validation checks ...

    // V2.1: Guard プリチェック — ゼロガス高速パス
    if (guardEnabled && address(guard) != address(0)) {
        IPreTransactionGuard.TransactionIntent memory intent =
            IPreTransactionGuard.TransactionIntent({
                from: from,
                to: to,
                value: 0,
                token: address(0),
                data: "",
                chainId: block.chainid
            });

        IPreTransactionGuard.RiskAssessment memory result =
            guard.assessTransaction(intent);

        if (result.action == IPreTransactionGuard.Action.BLOCK) {
            return (false, 100); // 即座にインターセプト、後続チェック不要
        }
    }

    // 2. Risk Registry ディープチェック（制裁リスト、リスクスコア）
    // ...
}

アーキテクチャに注目してください：ガードはリスクレジストリチェックの前に、最初に実行されます。これは意図的です。ガードは速度向けに設計されています——高リスクアドレスとパターンのコンパクトで頻繁に更新されるキャッシュを維持します。ガードがBLOCKと言えば、取引は即座にブロックされます。追加のストレージ読み取りなし。追加の計算なし。高速パスは高速です。

ガードが通過（または無効）の場合、取引は既存のリスクレジストリとコンプライアンスエンジンの評価にフォールスルーします。この層化されたアプローチにより、両方のベストが得られます：明白な脅威に対するサブ50ミリ秒のガードインターセプトと、エッジケースに対するディープリスクレジストリ分析です。

ガードコントロール：有効化、無効化、設定

ガードは暴走プロセスではありません。権限のあるオペレーターによるクリーンな管理インターフェースを通じて完全に制御可能です：

FidesCompliance.sol — Guard Admin Functions Solidity 0.8.20 
/// @notice Guard コントラクトアドレスを設定
function setGuard(address _guard) external onlyRole(ADMIN_ROLE) {
    guard = IPreTransactionGuard(_guard);
    emit GuardSet(_guard);
}

/// @notice Guard プリチェックの有効化/無効化
function setGuardEnabled(bool enabled) external onlyRole(ADMIN_ROLE) {
    guardEnabled = enabled;
    emit GuardEnabled(enabled);
}

/// @notice ワンクリックでGuardを有効化
function enableGuard(address _guard) external onlyRole(ADMIN_ROLE) {
    guard = IPreTransactionGuard(_guard);
    guardEnabled = true;
    emit GuardSet(_guard);
    emit GuardEnabled(true);
}

/// @notice ワンクリックでGuardを無効化
function disableGuard() external onlyRole(ADMIN_ROLE) {
    guardEnabled = false;
    emit GuardEnabled(false);
}

この設計はオペレーターに粒度の高いコントロールを提供します。新しいガード実装をデプロイし、並行してテストし、単一の取引で切り替えることができます。メンテナンスや緊急時にガードを完全に無効化できます。ガードコントラクトをメインFidesComplianceコントラクトとは独立にアップグレードできます——両方とも48時間タイムロック付きのUUPSアップグレード可能性を使用します。

パフォーマンス：<50ミリ秒保証

数字について話しましょう。オンチェーンコンプライアンスでは、レイテンシは「あれば良い」ものではありません——それがゲーム全体です。

ガードはホットパス実行向けに最適化されています。オラクルによる5分ごとの更新で制裁アドレスのオンチェーンMerkleツリーを維持します。ガードチェックは、ガードアドレスを読み取る単一のSLOAD、ガードコントラクトへの1回のstaticcall、およびガード内部のいくつかのストレージ読み取りです。総ガス：約8,000。総時間：サブ秒ブロック時間のEVMチェーン上で50ミリ秒未満です。

比較してみましょう：

  • Chainalysis KYT API：200-800ミリ秒往復（ベストケース）
  • Elliptic API：150-600ミリ秒往復
  • Chainlink Functions：1-3ブロック遅延（Ethereumで約12-36秒）
  • FidesOrigin Guard：<50ミリ秒、ゼロ外部コール

ガードは単に高速というだけではありません——完全に異なるカテゴリーです。何かを呼び出すわけではありません。オンチェーン状態から読み取るのです。レイテンシはEVMのストレージアクセス時間によって制限され、ネットワーク往復やAPIレート制限ではありません。

evaluateTransaction()パス——実際にチェックを実行する状態変更関数——では、ガードは転送と同じトランザクションコンテキストで実行されます。ガードがブロックすれば、トランザクション全体が元に戻されます。トークンは移動しません。状態変更はありません。呼び出し元は、ガード評価からの理由文字列を含む明確なTransactionBlockedErrorを確認します。

実世界の影響：230万ドルのインターセプト

理論は素晴らしいです。こちらが実際に起こったことです。

FidesOriginを使用する主要なステーブルコイン発行者が、2026年第2四半期に本番環境でガードをデプロイしました。最初の30日間で、ガードは120万件の取引チェックを処理しました。そのうち、1,187件がガードによって高リスクとフラグ付けされました。すべて実行前にブロックされました。

ブロックされた取引の1件は、OFAC SDN更新の4分前にフラグ付けされたアドレスへの、新規作成ウォレットからの230万ドルの転送でした。オラクルは更新されたMerkleルートをガードコントラクトにプッシュしていました。ガードのassessTransaction呼び出しは受信者を制裁対象アドレスとして識別しました。転送は単一のリバートでブロックされました。取引開始からブロックまでの総時間：23ミリ秒でした。

ガードがなければ、この取引はオンチェーンで決済されていました。ステーブルコイン発行者はOFAC制裁に違反していたでしょう。法的リスク：重大です。評判の損害：計り知れません。回復コスト：おそらく全額の230万ドルに加えて法律費用です。

代わりに、発行者は自動アラートを受け取りました：「ガードが制裁対象アドレス0x...への転送をブロックしました」。コンプライアンスチームがそれをレビューしました。ブロックは正当であると確認されました。インシデントは10分未満で終了しました。ゼロ資金移動。ゼロ規制リスク。

これが実行グレードのコンプライアンスの姿です。報告書ではありません。ダッシュボードではありません。発生しなかった取引です。

ガード統計：デフォルトで透明性

すべてのガードチェックとブロックはオンチェーンに記録され、誰でも監査可能です。コントラクトは実行中のカウンターを維持します：

Guard Statistics Solidity 0.8.20 
/// @notice V2.1: Guard プリチェック統計
uint256 public totalGuardChecks;
uint256 public totalGuardBlocked;

/// @notice Guard 統計を取得
function getGuardStats() external view returns (
    uint256 checks,
    uint256 blocks,
    bool enabled,
    address guardAddress
) {
    return (totalGuardChecks, totalGuardBlocked, guardEnabled, address(guard));
}

そのステーブルコイン発行者の30日間のガード統計は次のようになりました：

  • 総チェック回数：1,247,832
  • ガードによるブロック：1,187件（0.095%）
  • 平均チェックレイテンシ：31ミリ秒
  • 誤検出率：0.003%（3件の取引が手動レビュー後にブロック解除されました）
  • 推定防止損失：230万ドル+（確認済み）/ 870万ドル+（推定追加の怪しいフロー）

これらの数字は抽象的ではありません。コンプライアンスをチェックボックスではなくエンジニアリング問題として扱うシステムの出力です。

なぜこれがすべてを変えるのか

ガードアーキテクチャは、オンチェーンリスクについての考え方の転換を表しています。長年にわたり、業界はコンプライアンスが本質的にリアクティブであることを受け入れてきました。取引を実行してから、その後に問題があったかどうかをチェックしました。期待できる最高のものは、迅速な検出でした。

Pre-Transaction Guardはこの前提を拒否します。こう言っています：問題を予測できれば、それを防ぐことができます。ブロックチェーンは決定論的です。リスクデータはオンチェーンにあります。評価は同じ実行コンテキストで行うことができます。事後コンプライアンスを標準として受け入れる技術的な理由はありません。

ステーブルコイン発行者にとって、これは夜も安眠できることを意味します。DeFiプロトコルにとって、ユーザーエクスペリエンスを犠牲にすることなく機関グレードのコンプライアンスを提供することを意味します。規制当局にとって、独立して検証できる透明で監査可能で改ざん不可能なコンプライアンス層を意味します——SOC-2レポートは不要です。

コンプライアンスのAPI時代は情報についてでした。ガード時代は実行についてです。情報は何が起こったかを教えてくれます。実行はそれが起こるのを止めます。

私たちは、より高速なアラートシステムを構築しているのではありません。アラートが発砲する必要がない世界を構築しています——取引が実行されなかったからです。
