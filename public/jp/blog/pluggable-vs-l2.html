プラガブル合規モジュール
vs. 専用 L2

なぜ独自のチェーンを構築しなかったのか——そしてなぜあなたもそうすべきではないのか。オンチェーンコンプライアンスインフラにおけるモジュラ性の事例。

2025年初頭、私たちは根本的なアーキテクチャ上の決断に直面しました。FidesOrigin は注目を集めつつありました。ステーブルコイン発行体が統合について質問していました。問題は：どうやってデプロイするか？

私たちの前に2つの道がありました。パスA：専用の Layer 2 ブロックチェーン——すべてのトランザクションがネイティブにスクリーニングされる「コンプライアンスチェーン」を構築する。パスB：既存のチェーン上にプラガブルスマートコントラクトモジュールとしてデプロイする——Ethereum、Base、Polygon——どのトークンコントラクトも継承できます。

私たちはパスBを選びました。以下に、その理由と、なぜこれがオンチェーンコンプライアンスにとって唯一正しい選択であると信じているのかを説明します。

L2 の誘惑

専用 L2 アプローチは魅力的です。フルスタックを制御できます。チェーンをコンプライアンス専用に設計できます。すべてのトランザクションがデフォルトでスクリーニングされます。独自のコンセンサス、独自のガストークン、独自のバリデータセットを持ちます。要塞を構築しているような感覚です——完全で、突破不可能で、目的に特化しています。

いくつかのプロジェクトがこの道を歩みました。プレスリリースとトークンセールとともに「初のコンプライアンス特化 L2」を発表しています。ピッチは説得力があります：「私たちのチェーン上で構築すれば、コンプライアンスは自動的です。統合は不要。チェックを見逃すリスクはありません。」

しかし、問題があります。コンプライアンス L2 は、自身のチェーンと自身のチェーンのみのコンプライアンスを解決します。Ethereum メインネット上で構築しているステーブルコイン発行体は使用できません。Base 上の DeFi プロトコルは使用できません。Polygon 上の RWA トークナイゼーションプラットフォームは使用できません。コンプライアンス L2 は孤島です——そして孤島は建設が高価で、住むのが孤独です。

モジュラ性の論理

プラガブルモジュールアプローチはこう言います：新しいチェーンを構築するな。すべてのチェーンで動くコントラクトを構築しろ。 FidesOrigin は、アップグレード可能なスマートコントラクトのセットとしてデプロイされます——RiskRegistry、ComplianceEngine、PolicyEngine、Guard——任意の ERC20 または ERC721 コントラクトが私たちのインターフェースを継承することで統合できます。

以下が比較です：

次元専用 L2プラガブルモジュール
エコシステム依存ブリッジ、DEX、ウォレット、オラクルのブートストラップが必要なし——ユーザーのいる任意の EVM チェーンで動作
デプロイ時間6-12ヶ月（チェーン起動 + エコシステム）1-2週間（コントラクト統合）
運用コスト年間50万-200万ドル（バリデータ、インフラ、セキュリティ）年間約5万ドル（オラクル + 監視）
ユーザーフリクション資産のブリッジ、新しいウォレット、新しいガストークンゼロ——ユーザーは既存のトークンと同じように操作
マルチチェーン対応追加のブリッジが必要任意のチェーンに同じコントラクトをデプロイ
カスタマイズ性ワンサイズフィットオールのチェーンルールコントラクトごと、顧客ごとの設定
アップグレードパスハードフォークまたはチェーンマイグレーションUUPS プロキシ——48時間タイムロック、ダウンタイムなし
相互運用性L2 エコシステムに限定任意の DeFi プロトコルと合成可能

数字は明確です。専用 L2 は運用コストが10-40倍高く、デプロイに20倍の時間がかかり、到達可能な市場はわずかです。唯一の利点はコントロールです——そしてブロックチェーンにおいて、コントロールはしばしば資産ではなく負債です。

なぜエコシステム依存が L2 コンプライアンスを殺すのか

エコシステムの問題について詳しく説明しましょう。これは L2 アプローチで最も過小評価されているコストです。

ステーブルコイン発行体があなたのコンプライアンス L2 でローンチしたいと考えています。素晴らしい。しかし、彼らのユーザーは Ethereum メインネット上で USDC を保有しています。あなたの L2 でステーブルコインを使用するには、以下が必要です：

  • Ethereum からあなたの L2 へ USDC をブリッジ（ブリッジ手数料を支払い、確認を待つ）
  • あなたの L2 用のウォレットを設定（新しい RPC、新しいチェーン ID、新しいブロックエクスプローラー）
  • あなたのガストークンを取得（別のスワップ、別の手数料、別の学習曲線）
  • あなたのブリッジを信頼（独自のセキュリティ想定とハッキングの歴史がある）
  • あなたの L2 がダウンした場合、資金がアクセスできないことを受け入れる

各ステップがコンバージョンファネルです。各ステップで、ユーザーは脱落します。ステーブルコイン発行体はこのワークフローを見て、50-80%のユーザーロス率を見ています——誰かが最初のトランザクションを行う前に。彼らはコンプライアンスと非コンプライアンスの間で選んでいるのではありません。あなたのコンプライアンス孤島と、ユーザーがすでにいる Ethereum に留まることの間で選んでいるのです。

モジュールアプローチは、この摩擦を完全に排除します。ステーブルコインは Ethereum に残ります。コンプライアンスモジュールは Ethereum 上のコントラクトです。ユーザーは以前と全く同じようにステーブルコインとやり取りします——同じウォレット、同じガストークン、同じ DEX、同じすべて。コンプライアンスチェックは _update フックで透過的に行われます。トランザクションがブロックされない限り、ユーザーはそれが存在することすら知りません。

これは、ユーザーにあなたのところに来てもらうこととユーザーがすでにいる場所に行くことの違いです。後者が常に勝ちます。

ホットプラガブルアーキテクチャ：仕組み

プラガブルモジュールの技術的実装は、3つのコアパターンに基づいています：UUPS アップグレード可能性、独立したストラテジーコントラクト、および継承可能なコンプライアンスインターフェースです。

UUPS プロキシパターン

すべての FidesOrigin コントラクトは UUPS（Universal Upgradeable Proxy Standard）パターンを使用します。これは、コントラクトアドレスが変更されないが、実装ロジックをアップグレードできることを意味します。新しいバージョンの ComplianceEngine——改善されたリスクスコアリングや新しいポリシータイプを含む——をリリースする際、新しい実装をデプロイし、48時間タイムロックでアップグレードを提案し、実行します。コントラクトアドレスは同じままです。すべての統合トークンは自動的に新しいロジックを取得します。マイグレーションは不要です。ダウンタイムはありません。

FidesCompliance.sol — UUPS アップグレード認可Solidity 0.8.20
/**
 * @notice UUPS アップグレード認可 — ADMIN_ROLE のみがアップグレードを実行可能
 * @dev アップグレードタイムロックチェックを追加（48時間遅延）
 */
function _authorizeUpgrade(address newImplementation)
    internal override onlyRole(ADMIN_ROLE)
{
    bytes32 proposalId = implementationToProposal[newImplementation];
    require(proposalId != bytes32(0), "No upgrade proposal");
    uint256 executeAfter = upgradeProposals[proposalId];
    require(executeAfter != 0, "No upgrade proposal");
    require(block.timestamp >= executeAfter, "Upgrade timelock active");
    // 提案記録のクリーンアップ
    delete upgradeProposals[proposalId];
    delete implementationToProposal[newImplementation];
    emit UpgradeExecuted(proposalId, newImplementation);
}

48時間タイムロックは譲歩できません。統合プロトコルに新しい実装をレビューし、独自のテストを実行し、アップグレードを受け入れるかどうかを決定する時間を与えます。同意しない場合は、実装をフォークし、プロキシを独自のバージョンに向けることができます。モジュラ性は双方向に機能します——私たちがデフォルトを提供しますが、顧客が自身の運命を掌握します。

独立したストラテジーコントラクト

PolicyEngine コントラクトは、プラガブルストラテジーコントラクトに特定のルール評価を委譲します。各ストラテジーは IAssetCompliance インターフェースを実装し、独立して交換できます。顧客は、KYC 検証用のストラテジー、取引限度用のストラテジー、地理制限用のストラテジーを持つことがあります。コアコンプライアンスロジックに触れることなく、ストラテジーを追加、削除、または交換できます。

PolicyEngine — ストラテジーパターンSolidity 0.8.20
interface IAssetCompliance {
    enum Decision { ALLOW, WARN, BLOCK, HOLD }
    function checkTransfer(address from, address to, uint256 amount, address token) external view returns (Decision, string memory);
}
// 顧客が独自のストラテジーをデプロイ
contract CustomKYCTransferLimit is IAssetCompliance {
    uint256 public dailyLimit = 100000 * 1e18;
    mapping(address => uint256) public dailyTransferred;
    function checkTransfer(address from, address to, uint256 amount, address token) external view returns (Decision, string memory) {
        if (dailyTransferred[from] + amount > dailyLimit) {
            return (Decision.BLOCK, "Daily limit exceeded");
        }
        return (Decision.ALLOW, "");
    }
}

継承可能なコンプライアンスインターフェース

任意のトークンの統合ポイントは IFidesCompliance インターフェースです。ステーブルコインコントラクトはこのインターフェースを継承し、転送フックで evaluateTransaction() を呼び出します。このインターフェースは意図的に最小限です——3つの関数、クリーンな抽象化——そのため、統合には最小限のコード変更のみが必要です。

CompliantStableCoin.sol — 統合例Solidity 0.8.20
contract CompliantStableCoin is ERC20, IFidesCompliance {
    IFidesCompliance public fides;
    function _update(address from, address to, uint256 amount) internal override {
        if (from != address(0)) {  // ミントをスキップ
            (bool allowed, uint256 risk) = fides.evaluateTransaction(from, to, amount, address(this), 0);
            if (!allowed) revert ComplianceViolation(from, to, risk);
        }
        super._update(from, to, amount);
    }
}

これが統合のすべてです。開発者は1時間以内に既存の ERC20 に FidesOrigin コンプライアンスを追加できます。ブリッジは不要です。新しいチェーンは不要です。新しいガストークンは不要です。インターフェースをインポートし、フックを追加し、デプロイするだけです。

実際の顧客デプロイ

モジュラ性の論理は理論的なものではありません。3つの異なる顧客プロファイルでデプロイしました。それぞれ異なる要件とタイムラインを持っています。

顧客A：KYC + 限度額ステーブルコイン

ヨーロッパの電子マネー発行体は、基本的なコンプライアンスを備えたユーロ建てステーブルコインのローンチを希望していました：すべての保有者の KYC、毎日の転送限度額、地理制限（制裁対象国への取引不可）。機関顧客がそれを求めていたため、Ethereum メインネット上でローンチしました。

タイムライン：2日初回通話から本番デプロイまで。

Ethereum 上に FidesCompliance コントラクトをデプロイし、KYC ホワイトリストを持つ RiskRegistry を設定し、転送限度額を持つ PolicyEngine を設定しました（小売は毎日1万ユーロ、機関は毎日100万ユーロ）。ステーブルコインコントラクトは12行の Solidity で私たちのインターフェースを統合しました。法務チームが設定をレビューしました。監査人がコントラクトを検証しました。木曜日の午後に稼働しました。

コスト：デプロイガスで約3,000ドル（Ethereum メインネット、2026年4月）。継続的：オラクル更新と監視のため毎月2,000ドル。

L2 アプローチでは以下が必要でした：ブリッジの構築または提携、ユーザーに資金移動を説得、流動性のブートストラップ、6-12ヶ月の待機。ステーブルコインは2027年ではなく2026年にローンチします。市場機会は失われます。

顧客B：制裁 + ジオフェンシング RWA プラットフォーム

不動産やプライベートエクイティなどの実世界資産トークンをローンチするトークナイゼーションプラットフォームは、包括的な制裁スクリーニングに加えて地理的コンプライアンスが必要でした。ユーザーはグローバルに分布しています——米国、EU、シンガポール、UAE——それぞれの司法管轄区に異なる要件があります。

タイムライン：1週間要件定義から本番まで。

3つのチェーンに同時にデプロイしました：Ethereum（プライマリ）、Base（コスト効率の高い小売）、Polygon（機関）。各デプロイは同じコアコントラクトを使用しますが、異なる PolicyEngine 設定を使用します：米国の投資家は完全な OFAC + FinCEN スクリーニングを受け、EU の投資家は EU 制裁 + MiCA 取引報告を受け、シンガポールの投資家は MAS ガイドライン + ジオフェンシングを受けます。RWA トークンコントラクトはすべての3つのチェーンで同じインターフェースを継承します。

重要な洞察：モジュラ性により、コードをフォークすることなくデプロイごとに設定できます。同じコントラクト、異なるポリシー。3つのチェーン、1つのコードベース。専用 L2 では、（a）全員に対して単一のポリシー、または（b）3つの別々の L2 を実行する必要があります。

顧客C：フルカスタム DeFi プロトコル

コンプライアントなレンディングマーケットを構築する DeFi プロトコルは、標準モジュールを超えたいと考えていました。必要なもの：担保タイプに基づく動的リスクスコアリング、借り手の評判履歴、リアルタイムの市場状況。独自のオンチェーンアイデンティティシステムも統合したいと考えていました。

タイムライン：3週間SDK アクセスから本番まで。

SDK——完全なコントラクトソース、テストスイート、デプロイスクリプト——および拡張ポイントのドキュメントを提供しました。彼らのエンジニアリングチームは、レンディングロジック用のカスタム PolicyEngine ストラテジー、ID システム用のカスタム Oracle アダプター、リアルタイム市場リスク評価用のカスタム Guard モジュールを構築しました。Base（低ガス、高速ファイナリティ）にデプロイし、基本層の制裁スクリーニングとして RiskRegistry と統合しました。

SDK アプローチは、モジュラ性があるからこそ可能です。専用 L2 では、「カスタム」は（a）L2 チームにチェーンアップグレードを依頼し数週間待つ、または（b）チェーン全体をフォークすることを意味します。どちらも週次リリースの DeFi プロトコルにとって実行可能ではありません。

コストの現実

お金について話しましょう。ここが L2 の幻想が崩壊する場所です。

専用 L2 を実行することは高価です。以下は、中規模のコンプライアンス L2 の現実的なコスト内訳です：

  • バリデータインフラ：10-20のバリデータノード、各月2,000-5,000ドル = 年間24万-120万ドル
  • シーケンサー / プロポーザー：高可用性インフラ、年間5万-10万ドル
  • データ可用性：Ethereum L1 への投稿（ロールアップの場合）またはデータ可用性委員会 = 年間10万-50万ドル
  • ブリッジセキュリティ：マルチシグ、監視、保険 = 年間10万-30万ドル
  • エンジニアリングチーム：チェーンを維持する3-5名のプロトコルエンジニア = 年間60万-150万ドル
  • 法務 / コンプライアンス：チェーンの運営は規制の複雑さを増す = 年間20万-50万ドル

合計：年間130万-410万ドル——これは最初の有料顧客を獲得する前です。

対照的に、FidesOrigin のモジュールデプロイのコストは：

  • コントラクトデプロイ：ワンタイムのガス料金（チェーンあたり約3,000-10,000ドル）
  • オラクルインフラ：年間3万-5万ドル
  • 監視とアラート：年間1.5万-3万ドル
  • エンジニアリング：メンテナンスとアップグレード用に1-2名のエンジニア = 年間20万-40万ドル

合計：年間約25万-50万ドル——L2 アプローチよりおおよそ10分の1のコストで、顧客獲得の摩擦はほぼゼロです。

経済性は圧倒的です。モジュールアプローチはコスト、時間、リーチのすべてで桁違いに勝ちます。専用 L2 が意味を持つのは、ゼロからエコシステム全体を構築する場合のみです——それでも、チェーンをコントロールする増分価値に対して年間100万ドル以上の燃費を正当化する必要があります。

なぜモジュラ性が未来なのか

ブロックチェーン業界はモジュラ性に向かっています。Ethereum のロールアップ中心のロードマップ、Celestia のデータ可用性レイヤー、EigenLayer のリステーキング——トレンドは明確です。モノリシックチェーンは、組み合わせて機能する専門化されたレイヤーに道を譲っています。FidesOrigin のプラガブルコンプライアンスモジュールも、この同じアーキテクチャシフトの一部です。

私たちは独自のチェーンを必要としません。なぜならチェーンはすでに存在するからです。Ethereum は5,000億ドル以上の TVL、数千の dApp、DeFi で最も深い流動性を持っています。Base はサブセントのガスと Coinbase のディストリビューションを持っています。Polygon はエンタープライズパートナーシップと規制の明確さを持っています。これらは、私たちが複製する必要があるエコシステムではありません。私たちがサービスを提供するエコシステムです。

コンプライアンスプロトコルの仕事はチェーンになることではありません。すべてのチェーンをコンプライアントにすることです。それは、独自の島を構築する理由だったコンプライアンスを、すでに構築している場所に差し込めるモジュールに変えることです。

これは長期的に勝つアーキテクチャです。安いからではありません（そうですが）。デプロイが速いからでもありません（そうですが）。なぜなら、技術導入がどのように機能するかについての基本的な真実を尊重しているからです：人々は新しいプラットフォームにインフラのために移動しません。彼らは、すでにいる場所に来るインフラを採用します。

FidesOrigin は、あなたに私たちのチェーン上で構築するよう求めません。すでに使用しているチェーン上のコントラクトに3行のコードを追加するよう求めます。それがモジュラ性の約束です——そして私たちが L2 の道を決して考慮しなかった理由です。
