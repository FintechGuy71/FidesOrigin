即時記憶體池監控實現
零確認風險攔截

FidesOrigin如何監控記憶體池，在單一區塊確認之前就阻止風險交易——以及為什麼傳統的事後確認分析為時已晚。

FidesOrigin 工程 · 2026年8月 · 10分鐘閱讀

什麼是記憶體池？

在交易被納入區塊並提交到區塊鏈之前，它暫時存放在一個稱為記憶體池（memory pool）的暫存區中。每個全節點都維護著自己的記憶體池，這是一個等待被開採的待處理交易動態緩衝區。

當使用者廣播一筆交易時，它會透過點對點網路傳播，並進入數千個節點的記憶體池中。礦工從本地記憶體池中選擇交易納入下一個區塊，通常優先選擇Gas費最高的交易。在該區塊被開採之前，交易是「未確認」的——它存在於網路的意識中，但不在其永久記錄中。

這種未確認狀態既是特性也是漏洞。它是特性，因為它實現了快速傳播和費用市場動態。它是漏洞，因為記憶體池中的交易仍然可以執行——如果它的目的地是受制裁地址、釣魚合約或已知漏洞，等待區塊確認意味著損害已經造成。

零確認問題

傳統加密合規遵循一個簡單的工作流程：

  1. 交易被廣播到網路
  2. 交易被納入區塊（以太坊上12秒，比特幣上約10分鐘）
  3. 交易收到1-3次確認
  4. 風險平台針對資料庫查詢交易哈希
  5. 合規團隊審查警報
  6. 採取行動（如果有的話）

到第6步時，資金已經轉移。合規團隊正在記錄犯罪，而非預防犯罪。對於Base或Polygon等高速鏈，從廣播到最終確定的整個序列可能不到3秒。人工介入的合規無法跟上。

這就是零確認缺口：傳統工具在交易廣播到區塊納入之間的窗口期是盲目的，手動介入是不可能的。FidesOrigin透過將決策點從確認後移到納入前來彌補這個缺口。

關鍵洞察

在以太坊上，一筆標準的ERC-20轉帳在約12秒內確認。但交易在廣播後200-500毫秒內就在記憶體池中可見。這200毫秒的窗口就是FidesOrigin評估和攔截所需的全部時間。

MempoolWatcher架構

FidesOrigin MempoolWatcher是一個即時串流管道，透過WebSocket連接到全節點，攝取待處理交易，並在它們到達區塊之前根據風險註冊表進行評估。

1. 全節點WebSocket連接

Watcher透過WebSocket維護與每個支援網路上地理分佈的全節點的持久連接。我們使用eth_subscribe搭配newPendingTransactions主題，接收進入記憶體池的交易哈希串流。

WebSocket Subscription (TypeScript)
// Connect to Ethereum full node via WebSocket const ws = new WebSocket("wss://eth-mainnet.g.alchemy.com/v2/..."); ws.on("open", () => { ws.send(JSON.stringify({ jsonrpc: "2.0", id: 1, method: "eth_subscribe", params: ["newPendingTransactions"] })); }); ws.on("message", async (data) => { const { params: { result: txHash } } = JSON.parse(data); // txHash is a pending transaction — evaluate immediately await evaluateTransaction(txHash); });

2. 交易解析與解碼

每個待處理交易哈希立即透過eth_getTransactionByHash獲取，以檢索完整交易物件：發送者、接收者、價值、資料負載和Gas參數。對於ERC-20轉帳，輸入資料被解碼以提取實際的代幣接收者和轉帳金額。

3. 地址匹配與風險評分

一旦提取發送者和接收者地址，就會透過兩階段流程對照FidesOrigin風險註冊表進行檢查：

  • 第一階段——精確匹配：地址對照受制裁、釣魚和已知漏洞地址的熱點清單進行檢查。這是O(1)雜湊映射查詢，耗時<1毫秒。
  • 第二階段——GNN評分：對於不在熱點清單上的地址，圖神經網路評估地址的關係圖譜（交易鄰居、時間模式、交易對手風險）。這產生0-100的風險評分。
Risk Evaluation Pipeline
async function evaluateTransaction(txHash: string): Promise<RiskResult> { const tx = await provider.getTransaction(txHash); const { from, decodedTo, value } = parseTransaction(tx); // Phase 1: Exact match against hotlist const hotlistHit = await riskRegistry.isSanctioned(decodedTo); if (hotlistHit) { return { action: "BLOCK", reason: "SANCTIONED_ADDRESS", latencyMs: 12 }; } // Phase 2: GNN relationship scoring const score = await gnnModel.scoreAddress(decodedTo, { depth: 2, // 2-hop neighborhood timeWindow: "24h", minTxCount: 3 }); if (score.value > 85) { return { action: "QUARANTINE", reason: "HIGH_RISK_GNN", score, latencyMs: 67 }; } return { action: "PASS", score, latencyMs: 67 }; }

4. 警報與鏈上攔截

對於超過風險閾值的交易，存在兩條回應路徑：

  • 警報模式：交易被標記，並透過Webhook、PagerDuty或Slack發送警報。交易繼續進行但被記錄以供審查。
  • 攔截器模式：對於整合協議（例如CompliantStablecoin），觸發風控守衛模組。如果協議支援預檢，交易在智能合約層面被攔截，無法執行。

與Flashbots的關係

一個常見問題：記憶體池監控與Flashbots和MEV（最大可提取價值）有何關係？

Flashbots vs FidesOrigin MempoolWatcher

Flashbots監控記憶體池以提取價值——識別套利機會、三明治攻擊和清算利潤。其目標是經濟性的：在其他人之前捕獲MEV。

FidesOrigin MempoolWatcher監控記憶體池以防止傷害——識別受制裁地址、釣魚合約和可疑模式。其目標是保護性的：在壞交易確認前阻止它們。

兩者不是競爭對手。實際上，它們是互補的：

  • Flashbots保護協議經濟完整性（無搶先交易、公平排序）
  • FidesOrigin保護協議監管完整性（無受制裁地址、合規流）

Flashbots的私人記憶體池（Flashbots Protect）甚至可以增強FidesOrigin的有效性：如果協議將交易路由通過Flashbots Protect，FidesOrigin仍然可以監控公共記憶體池中的公共交易，同時協議自身的交易繞過公共MEV提取。

以太坊主網延遲細分（從WebSocket訊息接收到風險決策測量）：

  • 交易獲取：25-40毫秒（RPC往返）
  • 輸入解碼：1-3毫秒（本地ABI解析）
  • 熱點清單查詢：<1毫秒（記憶體內雜湊集合）
  • GNN評分：35-55毫秒（快取嵌入+推理）
  • 決策與警報：2-5毫秒
  • 總P99：97毫秒

在Base和Polygon等更快的鏈上，區塊時間為2-3秒，100毫秒評估窗口僅佔確認總時間的3-5%，為攔截留下充足的餘量。

局限性與權衡

記憶體池監控很強大，但並非萬能。我們相信透明地討論其邊界：

  • 私人記憶體池：透過Flashbots Protect或私人RPC（例如Taichi Network）發送的交易不會出現在公共記憶體池中。這些需要協議級整合（風控守衛模組）而非記憶體池監控。
  • 網路傳播差異：交易可能在到達某些節點之前先到達其他節點。Watcher必須連接到多個地理分佈的節點以最小化遺漏率。
  • 費用替換（RBF）：使用者可以用更高費用的版本替換待處理交易，可能改變接收者。Watcher追蹤交易nonce以檢測替換。
  • 延遲底線：RPC往返施加了延遲的物理底線。端到端亞50毫秒需要共置基礎設施，這在我們的企業級方案中可用。

結論

記憶體池是執行前風險控制的最後前沿。交易在記憶體池中花費的每一秒都是可以被評估、評分——以及如有必要——被阻止的一秒。

FidesOrigin的MempoolWatcher彌補了傳統事後分析無法解決的零確認缺口。結合鏈上風控守衛模組，它提供雙層防禦：在記憶體池中捕獲它，如果失敗，在合約中阻止它。

對於穩定幣發行方、DeFi協議和任何鏈上機構來說，這不是錦上添花。這是記錄違規的合規與預防違規的合規之間的區別。
