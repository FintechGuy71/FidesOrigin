1. Executive Summary

FidesOrigin is the first protocol-level solution for execution-grade programmable on-chain compliance.

Unlike existing Web3 compliance platforms that operate on a "monitor + alert + manual process" model, FidesOrigin embeds compliance enforcement directly into the transaction execution layer. When a user initiates a transfer, the protocol automatically evaluates risk, applies policy rules, and executes the decision on-chain. Off-chain data feeds (sanctions lists, risk scores) are synchronized periodically; their latency and coverage depend on the configured data sources.

The protocol addresses a critical gap in the Web3 compliance landscape: the structural disconnect between risk detection and risk enforcement. Current solutions (Chainalysis, TRM Labs, Forta) can identify suspicious activity, but they cannot prevent it at the smart contract level. By the time a compliance analyst reviews an alert, funds may have already moved through mixers, bridges, or decentralized exchanges.

FidesOrigin closes this gap with a vertically integrated stack: AI-powered risk models feed an Oracle network, which pushes risk labels on-chain in near real-time. Pluggable compliance modules (smart contracts) intercept every transaction before execution, applying deterministic policy rules with immutable audit trails.

2. Problem Definition

2.1 The Current State: Alert-Driven Compliance

The Web3 compliance market currently consists of 41+ platforms, all operating on fundamentally the same workflow:

User initiates transfer ↓ Chainalysis / TRM Labs monitors ↓ Risk alert generated ↓ Email sent to compliance team ↓ Analyst reviews (hours to days) ↓ Manual freeze / suspension ↓ Funds already moved (avg. 30 min)

This model was inherited from TradFi, where transactions take days to settle and manual review is operationally viable. In Web3, where settlement is near-instant and DeFi protocols run 24/7, the same approach creates an unbridgeable execution gap.

2.2 Core Pain Points

Structural Latency

Chain-off detection and chain-on enforcement are architecturally separated. By the time a human responds to an alert, the transaction has already settled on-chain — irreversibly.

Regulatory Accountability

Stablecoin issuers and RWA tokenization platforms face increasing regulatory pressure (MiCA, HKMA, SEC) to prove proactive compliance. "We tried our best" is not a defensible position when regulators demand proof of on-chain enforcement.

Operational Scalability

As transaction volumes grow, manual compliance review becomes a bottleneck. A single analyst can only review so many alerts per hour — and false positives consume disproportionate resources.

The "Transfer = Compliance" Gap

RWA tokenization requires that every transfer inherently satisfies compliance rules (KYC status, jurisdiction, holding limits). Existing solutions require post-transfer reconciliation, which violates the fundamental requirement.

3.3 Core Components

ComplianceEngine — Unified Entry Point

All compliance queries flow through a single entry point. Implements both IAssetCompliance and IWalletCompliance interfaces. Outputs a four-tier decision system: ALLOW / BLOCK / FLAG / HOLD.

RiskRegistry — On-Chain Risk Database

Stores address risk profiles, sanctions lists, entity tags, and contract risk scores. Role-based access control: ORACLE_ROLE for data updates, ADMIN_ROLE for emergency sanctions.

RiskProfile = {
  riskScore: 0-100,
  tier: UNKNOWN | LOW | MEDIUM | HIGH,
  tags: ["exchange", "whale", "mixer"],
  isSanctioned: bool,
  lastUpdated: timestamp
}

PolicyEngine — Strategy Evaluation Engine

Evaluates transactions against issuer-defined policies. Supports version control with automatic snapshots and one-click rollback. All policy changes are immutably recorded for regulatory audit.

RiskOracle — Off-Chain Data Bridge

Syncs risk data from off-chain sources (OFAC, Chainalysis, TRM Labs) to the on-chain RiskRegistry via Chainlink Functions. Features rate limiting, batch updates, and Merkle tree verification for data integrity.

3.4 Decision Flow

// Every transfer automatically triggers:
function _update(address from, address to, uint256 amount) internal override {
    if (from != address(0) && to != address(0) && complianceEnabled) {
        _checkCompliance(from, to, amount);
    }
    super._update(from, to, amount);
}

The evaluation order is strictly prioritized:

  1. Sanctions list check (highest priority)
  2. Amount limit verification
  3. Daily cumulative limit check
  4. Risk tier matching
  5. Mixer detection
  6. Contract risk assessment

4. Compliance & Regulatory Framework

4.1 HKMA Stablecoin Licensing

FidesOrigin's compliance stack is purpose-built to meet Hong Kong Monetary Authority (HKMA) stablecoin issuer licensing requirements. Key alignment areas include:

  • Reserve Management — On-chain reserve attestations with cryptographic proofs
  • AML Screening — Automated sanctions and PEP screening at the smart contract level
  • Redemption Controls — Programmable redemption gates with compliance pre-checks
  • Regulatory Reporting — Immutable audit trails accessible via GraphQL API

4.2 MiCA Compliance (EU)

The Markets in Crypto-Assets Regulation (MiCA) requires stablecoin issuers to maintain robust compliance frameworks. FidesOrigin provides:

  • On-chain reserve attestations with real-time verification
  • Transaction screening with immutable decision logs
  • Automated regulatory reporting via The Graph Subgraph
  • Geographic restriction enforcement at the protocol level
